# kana-decoder 仕様書 v0.1

- Status: Draft / 基本設計
- Version: 0.1.0
- 実装: C++コア + 安定したC API
- 実行環境: CPUのみ・完全オフライン
- 性能目標: 1文節あたり1 ms未満

## 1. 目的

kana-decoderは、ひらがなを中心とする日本語の読み列を、文脈に適合した漢字・かな表記および句読点を持つ文章へ変換する軽量デコーダである。単語単位の辞書置換ではなく、複数の読み候補、形態素接続、局所文脈、ホットワードを統合して最適な変換経路を選択する。大規模生成モデルやネットワーク接続を実行時の必須要件としない。

## 2. 設計目標と非目標

### 2.1 必須目標

1. ひらがな入力から漢字・ひらがな・カタカナを含む日本語表記を生成する。
2. 同音異義語を形態素接続と前後文脈に基づいて選択する。
3. ホットワードを再学習・通常辞書の再構築なしに追加、更新、削除できる。
4. 句読点および文境界を推定する。
5. CPUのみ、完全オフラインで動作する。
6. C++コアをC ABIから利用できる。
7. 1文節あたり1 ms未満を性能目標とし、再現可能なベンチマークで検証する。
8. 辞書・スコアリング・句読点推定を交換可能な構造にする。

### 2.2 非目標（v0.1）

- 音声認識、音響モデル、音声波形処理。
- 大規模LLMによる生成・推論。
- クラウド辞書やオンライン検索への依存。
- 初期段階での完全な日本語構文解析・意味理解。
- ユーザー入力を無条件に正しい文章へ書き換える生成的校正。
- v0.1時点での多言語対応。

## 3. 入出力モデル

### 3.1 入力

基本入力はUTF-8のひらがな列とする。句読点、空白、改行を含む入力も受け付け、明示的な区切りは推定より優先して保持する。

任意の入力コンテキスト:
- 直前までに確定した変換結果
- ドメインIDまたは辞書セットID
- ホットワードセット
- 文体ヒント（通常、口語、文書）
- 呼び出し元が指定する文境界ヒント

入力は原文バッファを保持し、変換結果から元の読み位置を追跡できること。

### 3.2 出力

- 正文化されたUTF-8テキスト
- 文節ごとの読み範囲と出力範囲
- 選択候補と代替候補（オプション）
- 推定信頼度またはスコア差（確率とは区別する）
- 句読点の挿入位置と理由コード（診断モード）

信頼度スコアを校正済み確率として扱ってはならない。

## 4. アーキテクチャ

処理パイプライン:

1. UTF-8検証・正規化
2. 読み辞書Trieによる候補列挙
3. 形態素候補のラティス構築
4. 品詞・活用・接続コストによる経路評価
5. 局所文脈およびホットワードによる再ランキング
6. 最良経路のデコード
7. 文節・文境界に基づく句読点推定
8. 出力整形とオフセット対応付け

各段階は独立した内部インターフェースを持つ。公開APIから特定の辞書形式やスコアリング実装を前提にしない。

### 4.1 候補ラティス

入力読み列の各位置をノードとし、読み範囲に一致する形態素候補を有向エッジとして表す。エッジは少なくとも以下を保持する。

- reading_start / reading_length
- surface
- lemmaまたはentry_id
- 品詞・活用属性
- left_context_id / right_context_id
- base_cost
- source（system dictionary / hotword / user dictionary）

候補生成はTrie等の前方一致構造を用いる。候補数の上限、探索ビーム幅、最大読み長は設定可能とし、上限到達時は診断情報を返す。上限による候補打ち切りを黙って成功扱いにしない。

### 4.2 経路選択

基本デコーダはViterbi型の動的計画法とする。経路コストが小さいものを優先する。

総コストの概念式:

C(path) = Σ lexical_cost + Σ connection_cost + Σ context_cost + Σ punctuation_cost - Σ hotword_bonus

各コストの尺度・重みは辞書またはモデルのバージョンに紐づける。異なる尺度のモデルを混在させない。v0.1では線形加算を基準とし、将来のスコアラー交換を妨げない。

### 4.3 文脈推定

文脈推定は、少なくとも次の特徴を利用可能にする。

- 直前・直後の形態素と品詞
- 活用・助詞・助動詞との接続
- 直近の確定文節
- ドメイン辞書・ホットワード
- 任意の文体ヒント

初期実装では局所特徴量と軽量な重みテーブルを用いる。文脈が不足する場合は辞書・接続コストを優先し、根拠の弱い意味推測で候補を過度に変更しない。

### 4.4 ホットワード

ホットワードは通常辞書とは別のオーバーレイとして管理する。エントリは読み、表記、品詞・接続属性、優先度、任意のドメインタグを持つ。

要件:
- 実行時の追加・更新・削除
- セッション単位またはエンジン共有のスコープ
- 通常辞書を変更しない
- 同一読みの複数表記を許容
- 優先度は接続可能性・文脈整合性を無条件に上書きしない
- デコード中は一貫した辞書スナップショットを参照
- 更新失敗時に既存辞書状態を破壊しない

実装候補はcopy-on-writeスナップショットまたは読み取り専用構造の世代切替とする。ロックフリー性は実測と安全性レビュー後に決定する。

### 4.5 句読点推定

句読点は独立した軽量段階で推定する。主な特徴:
- 文末表現・終助詞・助動詞
- 接続助詞や節境界
- 文節列の構造
- 明示的な入力句読点
- 文体ヒント

明示された句読点は保持し、重複挿入を避ける。読点は過剰挿入を避ける保守的な閾値を初期値とする。文末が未確定のストリーミング入力では暫定出力と確定出力を区別する。

## 5. 性能・資源要件

### 5.1 レイテンシ目標

主目標: 1文節のデコード処理時間を1 ms未満とする。

計測区間は、入力範囲が既知でエンジンが初期化済みの状態から、当該文節の候補生成・経路選択・局所文脈再ランキングが完了するまでとする。初期化、辞書ロード、ファイルI/O、呼び出し元のI/Oは別計測する。句読点処理を含む全体レイテンシも別指標として記録する。

報告値:
- p50 / p95 / p99
- 1文節あたり処理時間
- 文節長、候補数、ラティスエッジ数
- ホットワード件数
- CPU型番、クロック、OS、コンパイラ、最適化設定
- ウォームアップ回数、反復数

1 ms未満は目標であり、対象CPU・辞書規模・入力分布を定義したベンチマークで達成を確認するまでは保証値としない。

### 5.2 計算量・上限

候補数が増える場合に備え、最大候補数、ビーム幅、最大ラティスエッジ数を設ける。通常経路は入力長と候補数に対して概ね線形に近い処理量を目指す。上限到達時はステータスと診断フラグを返し、必要に応じて保守的なフォールバックを行う。

CPUのみで動作し、ネットワークアクセスを行わない。辞書はメモリマップまたは一括ロードを選択可能な構造を検討する。

## 6. C API設計方針

C ABIは公開境界とし、C++内部型を露出しない。エンジン・セッション・結果は不透明ハンドルで管理する。

初期API案:
- kd_engine_create(config, out_engine)
- kd_engine_destroy(engine)
- kd_session_create(engine, out_session)
- kd_session_destroy(session)
- kd_decode(session, input_utf8, input_length, options, out_result)
- kd_result_get_text(result, out_ptr, out_length)
- kd_result_get_segment_count(result, out_count)
- kd_result_get_segment(result, index, out_segment)
- kd_result_destroy(result)
- kd_hotword_upsert(engine_or_session, entry)
- kd_hotword_remove(engine_or_session, reading, surface)
- kd_get_version(out_version)

実際のヘッダーでは、すべての関数に戻り値ステータスを設ける。所有権、文字列寿命、スレッド安全性、NULL許容、ABI互換性を明文化する。呼び出し側が確保したバッファを利用できる取得APIも用意し、内部メモリの寿命を外部に漏らさない。

## 7. スレッド安全性

- エンジンの不変辞書データは複数セッションから共有可能とする。
- セッション状態は原則としてセッション所有者が管理する。
- 同一セッションへの同時decodeはv0.1では非対応、または明示的に直列化する。
- ホットワード更新とdecodeの並行実行では、各decodeが開始時点の一貫したスナップショットを参照する。
- destroyと他APIの同時実行は呼び出し側の同期責任とする。

## 8. 辞書・モデルのバージョニング

辞書パッケージには形式バージョン、エンコーディング、スコア尺度、品詞体系、生成ツールバージョン、チェックサムを含める。互換性のない辞書はロード時に拒否する。辞書ライセンスと出典をパッケージ単位で追跡する。

## 9. 品質評価とテスト

### 9.1 機能テスト群

- 基本かな漢字変換
- 同音異義語（例: はし、かえる、こうしょう）
- 助詞・活用・複合語の接続
- 固有名詞・専門用語のホットワード注入
- ホットワードの更新・削除・優先度競合
- 句読点・文末推定
- 明示句読点の保持
- 不明語のかなフォールバック
- UTF-8不正入力・空入力・長文入力
- 辞書破損・非互換バージョン
- 複数セッションと並行更新
- 出力オフセットの正当性

### 9.2 評価指標

- 文字誤り率（CER）
- 単語・文節単位の正解率
- 同音異義語選択正解率
- 句読点F1
- ホットワード適用正解率
- p50 / p95 / p99レイテンシ
- ピークRSS、辞書ロード時間

正解データは読み入力、期待出力、文脈、ドメイン、曖昧性ラベルを分離して保持する。文脈のない読みだけでは正解が一意でないケースを、単純な誤変換として数えない。

## 11. v0.1で未確定の設計判断

以下は根拠なく固定せず、試作と計測で決める。

- 採用する初期辞書とライセンス適合性
- 品詞体系・接続コスト形式
- C++標準の最終選択（初期実装はC++17以上を想定）
- 句読点モデルの特徴量と閾値
- ホットワードの最大件数と優先度スケール
- 対象CPU・OS・辞書サイズ別の性能保証プロファイル
- ストリーミング時の再変換範囲と確定タイミング

## 12. v0.1の受け入れ条件

- CPUのみ・オフラインでビルドおよび実行できる。
- C APIからエンジン生成、decode、結果取得、破棄ができる。
- 読み候補の複数経路を構築し、接続コストで選択できる。
- ホットワードを実行時に反映できる。
- 明示句読点を保持し、句読点推定の結果を返せる。
- 不明語や曖昧入力でクラッシュせず、保守的にフォールバックする。
- 性能測定が再現可能で、1文節1 ms未満の目標を評価できる。
- 辞書データのライセンスと由来が追跡できる。
